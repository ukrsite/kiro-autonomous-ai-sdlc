# Documentation Standards

This document defines the quality standards and formatting requirements for documentation generated by the WF5 Documentation workflow.

## Overview

All generated documentation must meet these standards to pass the accuracy validation checkpoint. Documentation should be clear, accurate, and useful for its target audience.

## General Standards

### Formatting

- Use Markdown format for all documentation files
- Use consistent heading hierarchy (`#` for title, `##` for sections, `###` for subsections)
- Use fenced code blocks with language identifiers for all code examples
- Use tables for structured data (parameters, return types, configuration options)
- Keep line length reasonable for readability (wrap at ~120 characters in prose)

### Language and Tone

- Use clear, concise technical language
- Write in present tense and active voice
- Avoid jargon without definition; include a glossary for domain-specific terms
- Use second person ("you") for instructional content (onboarding guides)
- Use third person for reference content (API docs)

### Accuracy

- All API signatures must match the actual source code exactly
- All code examples must be syntactically valid and runnable
- All file paths and module references must resolve to existing files
- Version numbers and dependency references must be current
- Configuration values must match actual defaults

## API Documentation Standards

### Required Sections per Public Interface

| Section | Description |
|---------|-------------|
| **Signature** | Full function/method/class signature with types |
| **Description** | One-paragraph summary of purpose and behavior |
| **Parameters** | Table listing each parameter: name, type, required/optional, description |
| **Returns** | Return type and description of the return value |
| **Raises/Throws** | Exceptions or errors that may be raised, with conditions |
| **Example** | At least one usage example with expected output |

### Class Documentation

- Document the class purpose and responsibilities
- Document the constructor with all parameters
- Document all public methods following the interface standard above
- Document public properties and attributes
- Note any inheritance or interface implementation

### Module Documentation

- Include a module-level docstring describing the module purpose
- List all public exports
- Describe module dependencies and relationships

## Architecture Diagram Standards

### Diagram Format

- Use Mermaid syntax for all diagrams (renders natively in Markdown viewers)
- Include a title and brief description above each diagram
- Use consistent naming conventions across diagrams
- Label all connections and relationships

### Required Diagram Types

| Diagram | Purpose |
|---------|---------|
| **Component Diagram** | Shows major components and their dependencies |
| **Module Interaction** | Shows how modules communicate and share data |
| **Data Flow** | Shows data movement through key workflows |
| **Layer Diagram** | Shows architectural layers and boundaries |

### Diagram Quality Criteria

- Components are labeled with descriptive names
- Relationships include directional arrows and labels
- External dependencies are clearly distinguished
- Diagram is not overly complex (max ~15 nodes per diagram; split if larger)

## Onboarding Guide Standards

### Required Sections

| Section | Description |
|---------|-------------|
| **Prerequisites** | Required tools, versions, and system requirements |
| **Installation** | Step-by-step setup instructions with commands |
| **Configuration** | Environment variables, config files, and settings |
| **Project Structure** | Directory layout with descriptions of key folders |
| **Running the Application** | Commands to build, run, and test |
| **Common Tasks** | Frequently performed development tasks |
| **Troubleshooting** | Common issues and their resolutions |

### Instructional Quality

- Every command must be copy-pasteable (use code blocks)
- Include expected output for verification steps
- Number all sequential steps
- Provide platform-specific instructions where behavior differs (Linux/macOS/Windows)

## Quality Metrics

| Metric | Target | Description |
|--------|--------|-------------|
| `api_coverage` | 100% | Percentage of public interfaces documented |
| `example_coverage` | ≥80% | Percentage of documented interfaces with examples |
| `signature_accuracy` | 100% | Percentage of signatures matching source code |
| `link_validity` | 100% | Percentage of internal links/references that resolve |
| `diagram_count` | ≥4 | Minimum number of architecture diagrams |
| `onboarding_sections` | 7 | All required onboarding sections present |
